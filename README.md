# promotion-go

![CI](https://github.com/kivenhuy/promotion-go/actions/workflows/ci.yml/badge.svg)

A backend service for running limited-stock promotion campaigns in games and web apps.

Handing out prizes is easy. Handing out a **fixed** number of prizes is not:

- thousands of users tap at the same moment when a campaign opens
- stock is finite and must **never** be over-issued
- each user has their own limit
- mobile networks drop, users retry, and a retry must not count twice

This service solves those four constraints. The first campaign type is a weighted lucky draw; the draw logic lives in the domain layer, so adding a new campaign type does not touch storage or the HTTP layer.

---

## API

```
POST /draws
     Idempotency-Key: <client-generated key>
     {"user_id": 1001, "campaign": "tet2026"}

201 Created   {"prize_id": 3, "name": "Sticker"}    first time
200 OK        {"prize_id": 3, "name": "Sticker"}    replay of a previous request
409 Conflict  {"error": "no prize available"}       out of stock, user limit reached,
                                                    or key belongs to another user
409 Conflict  {"error": "request in progress"}      same key is being processed right now;
                                                    retry after a short delay
400 Bad Req   {"error": "..."}                      malformed body
500            {"error": "lỗi hệ thống"}            internal error, details only in server logs

GET /healthz
```

## Layout

```
cmd/server        composition root: config, DB pool, signal handling, graceful shutdown
internal/api      HTTP: routing, middleware, DTOs, status-code mapping
internal/domain   business rules: weighted draw, prize invariants, sentinel errors
internal/store    persistence: Postgres queries, transactions
internal/idem     Redis guard in front of the store: dedup, replay, fail-open
migrations        goose migrations
```

Dependencies point inward. `api` declares the interface it needs; `store` satisfies it implicitly, and `idem` wraps `store` behind the same interface, so the handler cannot tell whether Redis is in the chain. `domain` imports nothing from the other two, so the draw algorithm is unit-testable without a database.

## Design decisions

### Optimistic concurrency control, not `SELECT ... FOR UPDATE`

Stock is decremented with a conditional update:

```sql
UPDATE gift_package SET win_quantity = win_quantity + 1
WHERE program_id = $1 AND package_id = $2 AND win_quantity < total_quantity
```

`RowsAffected() == 0` means someone took the last item, which maps to HTTP 409.

Optimistic and pessimistic locking both prevent over-issuing, but pessimistic locking holds the row from the `SELECT` until the commit. That window includes the time spent checking availability, evaluating the weighted draw, and picking the prize — all of it in Go, none of it needing a lock. Since `gift_package` is the hottest row in the system, that window dominates throughput. The conditional update holds the lock only for the duration of a single statement, and leaves the read path free to move to a replica later.

This works here because the business rule — *there must be stock left* — can be re-checked by the database at write time. The draw result only decides **which row** to update, not whether the update is valid.

It would be the wrong choice for a different draw model. If prizes came from a pre-shuffled fixed pool where everyone claims the next free slot, every request would target the same row. Most would lose the conditional update and retry, and throughput would collapse under load. That model is better served by `SELECT ... FOR UPDATE SKIP LOCKED`, which hands each concurrent request a different slot instead of making them compete for one.

### Reads stay outside the transaction

`availablePrize` and the weighted draw run before `BeginTx`. An open transaction holds a database connection for its entire lifetime, and neither the read nor the draw needs one.

A stale read is acceptable here precisely because the write re-validates the condition. The read is a hint, not a guarantee.

### Idempotency is the first statement in the transaction

Each request carries an `Idempotency-Key` header generated by the client **once per user intent**, not once per HTTP call — every retry sends the same key.

The transaction starts by inserting that key. On a unique violation (SQLSTATE `23505`) the request has been served before: roll back, read the stored result, return it with **200** instead of 201. The user learns what they won, which is exactly what they need after a dropped connection.

It runs first so a duplicate is rejected **before** touching `gift_package`, the row everyone else is contending for.

Two concurrent requests with the same key are serialized by the database itself. The second insert blocks until the first transaction finishes, so it can never read a half-written record:

| First transaction | Second request sees | Outcome |
|---|---|---|
| commits | `23505` | replays the stored result |
| rolls back | insert succeeds | processed as a fresh request |

No application-level locking is needed for this.

### Lock ordering

Inside the transaction, statements run in a fixed order:

```
1. INSERT idempotency_record    cheap, rejects duplicates early
2. UPSERT user_quota            contended by one user only
3. INSERT draw_log              append-only, nobody contends for it
4. UPDATE gift_package          contended by EVERYONE — last, so its lock spans only this statement and the commit
```

Two reasons. The hottest row is locked last and held for the least time: everything that can be written without contention is written before it, so once the row lock is taken the only thing left is the commit. And a fixed order across the whole codebase is what prevents deadlocks — any future operation touching these tables must follow it.

The log row is written before the stock is known to be available. That is safe because it lives inside the transaction: if the conditional update affects zero rows the function returns an error, the deferred rollback discards the log row with everything else, and nothing outside the transaction ever saw it. Originally the log came after the update; under load `pg_stat_activity` showed transactions queueing on the `gift_package` row while the holder was still inserting its log row, which is why it moved.

### Per-user limits in one statement

```sql
INSERT INTO user_quota (user_id, program_id, package_id, used)
VALUES ($1, $2, $3, 1)
ON CONFLICT (user_id, program_id, package_id)
DO UPDATE SET used = user_quota.used + 1, updated_at = now()
WHERE user_quota.used < $4
```

Create-or-increment-or-reject in a single atomic statement. A `SELECT` followed by `INSERT`/`UPDATE` leaves a window where two concurrent requests both see "no row yet" and both insert — one of them then fails with a unique violation and the user gets a 500 instead of a clear answer.

### Defense in depth

The schema carries the invariant independently of application code:

```sql
CONSTRAINT chk_win_le_total CHECK (win_quantity <= total_quantity)
```

This is not decoration. Mutation testing (below) confirmed it: with the `WHERE` clause removed from the update, the CHECK constraint still prevented over-issuing.

### Separate table for idempotency keys

Keys live in `idempotency_record`, not as a column on `draw_log`, because the two have different lifetimes: audit logs are kept indefinitely, keys expire after ~48h and are swept by a cleanup job. Keeping them together would mean a unique index over the entire log history, and would break once `draw_log` needs partitioning — unique constraints do not hold across partitions.

### Redis as a first-line filter, not a source of truth

A Redis guard sits in front of the Postgres store. The first request for an `Idempotency-Key` runs `SET key "processing" NX EX 10`; after the transaction commits, the result is written back under the same key with a 48-hour TTL. Retries are then answered from Redis without opening a transaction, and a retry storm from a misbehaving client never reaches the connection pool.

Redis does not replace the unique index. `SET NX` returns immediately instead of blocking, nothing is rolled back when the transaction fails (the guard deletes the key by hand), and keys expire. Correctness is still enforced only in the database; Redis makes the common path cheaper.

Two consequences follow.

**Fail-open needs a timeout.** Every Redis call is capped at 50 ms; on error or timeout the request goes straight to Postgres. The fail-open test asserts total latency under 500 ms with Redis unreachable. Before the per-call timeout existed, that test measured 3.5 s for two requests: go-redis retried the dial five times, so a dead Redis would have slowed every request by ~1.7 s without failing a single one.

**Short TTLs are safe because the database is the backstop.** If the `processing` key expires while the first transaction is still running, the retry falls through to Postgres, blocks on the unique index, and is replayed correctly. A long TTL buys nothing here and costs a lockout: after a crash, retries would be rejected as "in progress" until the key expired.

### Shed load instead of queueing it

Go starts a goroutine per connection and never says no, so under overload every request is accepted and then waits: for a pool connection, for a row lock, for the commit. Under a 1,200 req/s run the slowest request spent 10.7 s inside the handler before getting an answer it could have had in 2 ms.

`/draws` now sits behind a concurrency limit implemented as a channel semaphore: at most `MAX_INFLIGHT` requests (default 50, twice the database pool) are inside the handler at once, and the next one gets a `503` with `Retry-After: 1` without waiting. `/healthz` is deliberately outside the limit, so a load balancer never mistakes an overloaded instance for a dead one and shifts its traffic onto the others.

This is a concurrency limit, not a rate limit. It counts requests in progress, not requests per second, so it adapts on its own: when the database is fast, 50 slots carry thousands of requests per second; when it slows down, the slots fill and the limiter starts refusing at exactly the rate the system can no longer absorb. The test for it holds two fake requests inside the handler with a channel, checks that a third is refused in under 50 ms, releases the two, and checks that a fourth is admitted; removing the slot release makes only that last assertion fail.

## Schema

```
gift_package        (program_id, package_id)                prize config + stock counter
user_quota          (user_id, program_id, package_id)       per-user usage
draw_log            log_id                                  append-only audit trail
idempotency_record  key                                     request dedup, TTL ~48h
```

Composite primary keys, not surrogate ids: the natural key *is* the identity, and it gives the uniqueness guarantee for free.

## Testing

```bash
go test -race -count=5 ./...
```

`-count=5` is deliberate. Concurrency tests are not deterministic — a race only surfaces when timing is unfavourable, and a single green run proves very little.

Integration tests run against a real Postgres and a real Redis. They skip cleanly when neither is reachable, so `go test ./...` stays green on a machine without them, and they **fail** instead of skipping when `CI=true`, so a broken CI setup can never produce a green run with no tests executed. Each test seeds its own campaign or key named after `t.Name()`, so tests never collide and can run in parallel.

Three store tests cover the hard parts of the transaction:

| Test | Asserts |
|---|---|
| same key twice | second call is a replay, stock decremented **once** |
| 1 item, 10 concurrent users | exactly 1 winner, `win_quantity = 1`, and **1 row** in `user_quota` — the 9 failed transactions rolled back cleanly |
| per-user limit of 2, 3 attempts | third attempt rejected, stock untouched |

Each test asserts both the returned value **and** the persisted state. A function returning `nil` only means it ran without error; it does not mean the data landed where it should. A forgotten `tx.Commit()` passes the first check and fails the second.

Five guard tests replace the store with a counting fake, because the guard's only job is deciding whether to call it:

| Test | Asserts |
|---|---|
| same key twice | store called **once**, second result is a replay |
| Redis unreachable | store called twice, no error surfaces, both calls finish in **under 500 ms** |
| store returns an error | key is deleted, so the retry is not rejected as "in progress" |
| another user reuses the key | rejected from Redis, store not called |
| 10 goroutines, same key | store called exactly once; the other nine are either replays or "in progress", in a ratio that varies per run |

### Mutation testing

The tests were validated by deliberately breaking the code and confirming they go red:

| Mutation | Result |
|---|---|
| remove `tx`, use the pool directly for the quota upsert | caught — `user_quota` left 10 rows instead of 1 |
| remove `WHERE win_quantity < total_quantity` | caught in 7/8 runs — the CHECK constraint fires instead, surfacing as an unexpected SQLSTATE rather than a clean 409 |
| guard: skip writing the result back to Redis | caught — the key stays `processing`, so the retry is rejected instead of replayed |
| guard: reuse one cancelled context for all Redis calls | caught — every call after the first fails with `context canceled`, the store is called twice |
| guard: no per-call timeout | caught by the 500 ms assertion — 3.5 s for two requests with Redis down |

The second one is why the concurrency test distinguishes *expected* errors from *any* error. Counting failures alone would have passed. The last two were not deliberate mutations: they were real bugs the tests caught during development, and the reason the fail-open test asserts on time.

## Observability

Both endpoints live on a separate debug port (`DEBUG_ADDR`, off unless set, bound to loopback in `compose.yml`), never on the public listener.

**`/debug/pprof/`** is the standard Go profiler. A 30-second CPU profile under steady load is what showed that the application's own CPU goes to syscalls, not to JSON or logging.

**`/metrics`** exposes three Prometheus series following the RED pattern:

| metric | type | labels | answers |
|---|---|---|---|
| `http_requests_total` | counter | `route`, `status` | rate and error ratio |
| `http_request_duration_seconds` | histogram | `route` | p50/p99 via `histogram_quantile` |
| `http_requests_shed_total` | counter | | how often the inflight limiter refused |

`route` is the matched mux pattern (`POST /draws`), not the raw path, so a future `/users/{id}` cannot explode label cardinality. The histogram buckets run from 1 ms to 5 s because that is the range the load tests showed this service actually occupies.

A 60-second run at 400 req/s reconciled to the request: k6 reported 24,000 requests with 90 failures; `/metrics` reported 23,801 × 201, 109 × 409, 90 × 503 and `http_requests_shed_total 90`, with 81% of requests under 2.5 ms and all under 500 ms.

```promql
histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket{route="POST /draws"}[1m])) by (le))
```

## Running locally

```bash
brew install postgresql@17 goose redis
brew services start redis
createdb luckydraw

export DATABASE_URL="postgres://$USER@localhost:5432/luckydraw?sslmode=disable"
```

## Known limits

Measured on a 2 vCPU / 4 GB VPS running app, Postgres and Redis together via Compose (`compose.yml`), with k6 ramping to 100 VUs over 70 s (`loadtest/draw.js`) and prize stock large enough that every request takes the full transactional path:

| | from a laptop over an SSH tunnel | k6 on the same host |
|---|---|---|
| requests / s (avg over ramp) | 644 | 625 |
| p50 / p95 / p99 | 48 ms / 180 ms / < 500 ms | 48 ms / 191 ms / 291 ms |
| 5xx | 0 | 0 |

Across 94,286 successful draws the stock counters, `draw_log` and `idempotency_record` matched to the row, and the prize split was 28/72 against configured weights of 30/70.

One caveat: the minimum latency was 1.7 ms, so most of that p50 is queueing introduced by the measurement setup, not service time. The VU ramp is also a closed loop, so the server throttles the load generator when it slows down and the numbers flatter it.

An open-loop test (`loadtest/ceiling.js`, `constant-arrival-rate`, k6 on the same host) finds the knee:

| target rate | baseline: p50 / p99 | `INSERT draw_log` moved ahead of the hot update | + inflight limit of 50 (load shedding) |
|---|---|---|---|
| 400 req/s | 2.3 ms / 306 ms | 2.3 ms / 454 ms | 2.5 ms / 84 ms |
| 600 req/s | 314 ms / 1.29 s | **4.6 ms / 102 ms** | 4.4 ms / 121 ms |
| 800 req/s | 1.22 s / 5.1 s, 5,922 dropped | 990 ms / 4.33 s, 3,407 dropped | **63 ms / 211 ms**, 0 dropped, 11% of requests shed with 503 |

Two changes, each measured on its own. Reordering one statement so that the `gift_package` row lock spans only the update and the commit (see *Lock ordering*) moved the knee past 600 req/s: at that rate p99 fell from 1.29 s to 102 ms with no other change. 800 req/s was still over the knee. Adding a concurrency limit of 50 in-flight requests on `/draws` (see *Shed load instead of queueing it*) then turned the 800 req/s case from "everyone waits 4 s" into "89% are served with p99 of 211 ms and 11% get a 503 in microseconds". The served throughput settles at roughly the knee, which the limiter finds on its own: requests only pile up when the database slows down. The slowest request measured **inside the handler** was 10.7 s during the 1,200 req/s run: requests were queueing for a pool connection while 25 transactions shared two cores with Postgres and the load generator. Pool exhaustion showed up as the symptom, exactly as predicted below. Because k6 shares the box, these are lower bounds.

With the load generator moved off the box (laptop over an SSH tunnel, which itself collapsed above ~400 req/s), the picture changed: at 400 req/s Postgres sat at 62% CPU and `pg_stat_activity` showed **10 backends waiting on `transactionid` and 3 on `tuple` locks**, with request latency spiking to 1.5 s while total CPU was still under 120% of 200%. That is the hot-row contention predicted below, surfacing before CPU runs out. At that point the lock on `gift_package` was held from the `UPDATE` through `INSERT draw_log` to the commit fsync. Inserting the log row before the hot update is what produced the "after" column above. The remaining lever is the commit itself: relaxing `synchronous_commit` would shorten the lock further, at the cost of losing the last few milliseconds of commits on a crash, which a prize with real value cannot accept.

A CPU profile taken under steady load put `encoding/json` and `slog` nowhere near the top: the application's own CPU is dominated by syscalls to Postgres and Redis. The earlier guess that JSON logging was the cost was wrong, which is the reason to profile instead of guess.

During the run the app container used ~70% CPU, Postgres ~25%, Redis ~20%. At this rate row-lock contention on `gift_package` did not surface; the first optimization target is per-request work in the application (one JSON log line per request, two to three Redis round-trips), not the database.

```bash
k6 run loadtest/draw.js                      # BASE defaults to http://localhost:8090
```

**Beyond that point, the expected bottleneck is row-lock contention, not the connection pool.** Every request for a popular prize updates the same `gift_package` row, and Postgres serializes those updates. Adding application instances does not help: ten servers writing to one row still queue behind the same lock.

Pool exhaustion is the symptom that shows up first in monitoring, and raising `MaxOpenConns` makes it worse — more transactions competing for the same row means a longer lock queue.

Mitigations, cheapest first:

1. keep transactions short (already done — reads and the draw run outside)
2. move reads to a replica
3. count in Redis, flush to Postgres periodically — trades exactness for throughput
4. sharded counters — splits the hot row, but introduces false out-of-stock and makes every report an aggregate
5. pre-allocated prize pool with `SKIP LOCKED` — removes contention entirely, at the cost of fixing the prize distribution up front

Most systems never need past step 2. Steps 4 and 5 require changing the data model, not the queries — no SQL syntax makes a thousand writes to one row go faster.
