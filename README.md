# promotion-go
![CI](https://github.com/kivenhuy/promotion-go/actions/workflows/ci.yml/badge.svg)


A backend service for running limited-stock promotion campaigns in games and web apps.

Handing out prizes is easy. Handing out a **fixed** number of prizes is not:

- thousands of users tap at the same moment when a campaign opens
- stock is finite and must **never** be over-issued
- each user has their own limit
- mobile networks drop, users retry, and a retry must not count twice

This service solves those four constraints. The first campaign type is a weighted lucky draw; the draw logic lives in the domain layer, so adding a new campaign type does not touch storage or the HTTP layer.

---

## API

```
POST /draws
     Idempotency-Key: <client-generated key>
     {"user_id": 1001, "campaign": "tet2026"}

201 Created   {"prize_id": 3, "name": "Sticker"}    first time
200 OK        {"prize_id": 3, "name": "Sticker"}    replay of a previous request
409 Conflict  {"error": "no prize available"}       out of stock, user limit reached,
                                                    or key belongs to another user
400 Bad Req   {"error": "..."}                      malformed body
500            {"error": "lỗi hệ thống"}            internal error, details only in server logs

GET /healthz
```

## Layout

```
cmd/server        composition root: config, DB pool, signal handling, graceful shutdown
internal/api      HTTP: routing, middleware, DTOs, status-code mapping
internal/domain   business rules: weighted draw, prize invariants, sentinel errors
internal/store    persistence: Postgres queries, transactions
migrations        goose migrations
```

Dependencies point inward. `api` declares the interface it needs; `store` satisfies it implicitly. `domain` imports nothing from the other two, so the draw algorithm is unit-testable without a database.

## Design decisions

### Optimistic concurrency control, not `SELECT ... FOR UPDATE`

Stock is decremented with a conditional update:

```sql
UPDATE gift_package SET win_quantity = win_quantity + 1
WHERE program_id = $1 AND package_id = $2 AND win_quantity < total_quantity
```

`RowsAffected() == 0` means someone took the last item, which maps to HTTP 409.

Optimistic and pessimistic locking both prevent over-issuing, but pessimistic locking holds the row from the `SELECT` until the commit. That window includes the time spent checking availability, evaluating the weighted draw, and picking the prize — all of it in Go, none of it needing a lock. Since `gift_package` is the hottest row in the system, that window dominates throughput. The conditional update holds the lock only for the duration of a single statement, and leaves the read path free to move to a replica later.

This works here because the business rule — *there must be stock left* — can be re-checked by the database at write time. The draw result only decides **which row** to update, not whether the update is valid.

It would be the wrong choice for a different draw model. If prizes came from a pre-shuffled fixed pool where everyone claims the next free slot, every request would target the same row. Most would lose the conditional update and retry, and throughput would collapse under load. That model is better served by `SELECT ... FOR UPDATE SKIP LOCKED`, which hands each concurrent request a different slot instead of making them compete for one.

### Reads stay outside the transaction

`availablePrize` and the weighted draw run before `BeginTx`. An open transaction holds a database connection for its entire lifetime, and neither the read nor the draw needs one.

A stale read is acceptable here precisely because the write re-validates the condition. The read is a hint, not a guarantee.

### Idempotency is the first statement in the transaction

Each request carries an `Idempotency-Key` header generated by the client **once per user intent**, not once per HTTP call — every retry sends the same key.

The transaction starts by inserting that key. On a unique violation (SQLSTATE `23505`) the request has been served before: roll back, read the stored result, return it with **200** instead of 201. The user learns what they won, which is exactly what they need after a dropped connection.

It runs first so a duplicate is rejected **before** touching `gift_package`, the row everyone else is contending for.

Two concurrent requests with the same key are serialized by the database itself. The second insert blocks until the first transaction finishes, so it can never read a half-written record:

| First transaction | Second request sees | Outcome |
|---|---|---|
| commits | `23505` | replays the stored result |
| rolls back | insert succeeds | processed as a fresh request |

No application-level locking is needed for this.

### Lock ordering

Inside the transaction, statements run in a fixed order:

```
1. INSERT idempotency_record    cheap, rejects duplicates early
2. UPSERT user_quota            contended by one user only
3. UPDATE gift_package          contended by EVERYONE — touched last, held shortest
4. INSERT draw_log
```

Two reasons. The hottest row is locked last and held for the least time. And a fixed order across the whole codebase is what prevents deadlocks — any future operation touching these tables must follow it.

### Per-user limits in one statement

```sql
INSERT INTO user_quota (user_id, program_id, package_id, used)
VALUES ($1, $2, $3, 1)
ON CONFLICT (user_id, program_id, package_id)
DO UPDATE SET used = user_quota.used + 1, updated_at = now()
WHERE user_quota.used < $4
```

Create-or-increment-or-reject in a single atomic statement. A `SELECT` followed by `INSERT`/`UPDATE` leaves a window where two concurrent requests both see "no row yet" and both insert — one of them then fails with a unique violation and the user gets a 500 instead of a clear answer.

### Defense in depth

The schema carries the invariant independently of application code:

```sql
CONSTRAINT chk_win_le_total CHECK (win_quantity <= total_quantity)
```

This is not decoration. Mutation testing (below) confirmed it: with the `WHERE` clause removed from the update, the CHECK constraint still prevented over-issuing.

### Separate table for idempotency keys

Keys live in `idempotency_record`, not as a column on `draw_log`, because the two have different lifetimes: audit logs are kept indefinitely, keys expire after ~48h and are swept by a cleanup job. Keeping them together would mean a unique index over the entire log history, and would break once `draw_log` needs partitioning — unique constraints do not hold across partitions.

## Schema

```
gift_package        (program_id, package_id)                prize config + stock counter
user_quota          (user_id, program_id, package_id)       per-user usage
draw_log            log_id                                  append-only audit trail
idempotency_record  key                                     request dedup, TTL ~48h
```

Composite primary keys, not surrogate ids: the natural key *is* the identity, and it gives the uniqueness guarantee for free.

## Testing

```bash
go test -race -count=5 ./...
```

`-count=5` is deliberate. Concurrency tests are not deterministic — a race only surfaces when timing is unfavourable, and a single green run proves very little.

Integration tests run against a real Postgres and skip cleanly when none is reachable, so `go test ./...` stays green on a machine without a database. Each test seeds its own campaign named after `t.Name()`, so tests never collide and can run in parallel.

Three tests cover the hard parts:

| Test | Asserts |
|---|---|
| same key twice | second call is a replay, stock decremented **once** |
| 1 item, 10 concurrent users | exactly 1 winner, `win_quantity = 1`, and **1 row** in `user_quota` — the 9 failed transactions rolled back cleanly |
| per-user limit of 2, 3 attempts | third attempt rejected, stock untouched |

Each test asserts both the returned value **and** the persisted state. A function returning `nil` only means it ran without error; it does not mean the data landed where it should. A forgotten `tx.Commit()` passes the first check and fails the second.

### Mutation testing

The tests were validated by deliberately breaking the code and confirming they go red:

| Mutation | Result |
|---|---|
| remove `tx`, use the pool directly for the quota upsert | caught — `user_quota` left 10 rows instead of 1 |
| remove `WHERE win_quantity < total_quantity` | caught in 7/8 runs — the CHECK constraint fires instead, surfacing as an unexpected SQLSTATE rather than a clean 409 |

The second one is why the concurrency test distinguishes *expected* errors from *any* error. Counting failures alone would have passed.

## Known limits

Not yet measured under load. The numbers below are reasoning, not benchmarks.

**The expected bottleneck is row-lock contention, not the connection pool.** Every request for a popular prize updates the same `gift_package` row, and Postgres serializes those updates. Adding application instances does not help: ten servers writing to one row still queue behind the same lock.

Pool exhaustion is the symptom that shows up first in monitoring, and raising `MaxOpenConns` makes it worse — more transactions competing for the same row means a longer lock queue.

Mitigations, cheapest first:

1. keep transactions short (already done — reads and the draw run outside)
2. move reads to a replica
3. count in Redis, flush to Postgres periodically — trades exactness for throughput
4. sharded counters — splits the hot row, but introduces false out-of-stock and makes every report an aggregate
5. pre-allocated prize pool with `SKIP LOCKED` — removes contention entirely, at the cost of fixing the prize distribution up front

Most systems never need past step 2. Steps 4 and 5 require changing the data model, not the queries — no SQL syntax makes a thousand writes to one row go faster.
